Phase 11 - Hardware plausibility validation with Windows EMI
============================================================

Purpose
-------
Phase 11 now contains both the Windows energy-source validation and the final
100/500/1000 end-to-end plausibility test.

Validated Dell reference source
-------------------------------
Windows EMI has already passed the source-level Dell plausibility check:
- EMI v2 is present.
- Primary channel: RAPL_Package0_PKG.
- Native unit: picowatt-hours.
- AbsoluteEnergy is monotonic in the performed validation.
- Mean package power increased from approximately 7.155 W at idle to 47.916 W

1. Verify Windows EMI before a benchmark session
------------------------------------------------
From the repository root:

    python -m bench.tools.windows_emi_probe --interval-s 2

Expected on the reference Dell:
- available: true
- primary_domain: RAPL_Package0_PKG
- positive delta_energy_j
- positive sensor_duration_s

Optional hardware pytest:

    python -m pytest bench/tests/integration/test_windows_emi_energy_hardware.py -v

2. Run the controlled Phase 11I benchmarks
------------------------------------------
The supplied YAML files explicitly pin Windows EMI and the package channel:

    metrics.energy.backend: windows_emi
    metrics.energy.emi_channel: RAPL_Package0_PKG

Run:

    python -m bench.cli.bench phase11_configs/energy_plausibility_n100.yaml
    python -m bench.cli.bench phase11_configs/energy_plausibility_n500.yaml
    python -m bench.cli.bench phase11_configs/energy_plausibility_n1000.yaml

Keep model, input, precision, backend, device, threads, Windows power scheme, AC
state, Dell thermal mode, placement/cooling and avoidable background load constant.

3. Inspect each bench.json
--------------------------
For all three runs require:

    metrics.energy.available == true
    metrics.energy.backend == "windows_emi"
    metrics.energy.primary_domain == "RAPL_Package0_PKG"
    metrics.energy.total_energy_j > 0
    metrics.energy.inference_count == 100 / 500 / 1000 respectively

For EMI, duration_source should normally be backend_counter. The independent
wall_clock_duration_s is retained as an audit value.

Real Phase 11I Dell result (27.10.2026)
-------------------------------------------
The updated pipeline was executed on the Dell reference system with the supplied
100/500/1000 configurations. All three results used windows_emi and
RAPL_Package0_PKG and reported available=true.

    N=100:  3.614921 J total, 36.1492 mJ/inference, 32.6325 W, 0.110777 s
    N=500: 19.442225 J total, 38.8844 mJ/inference, 48.5633 W, 0.400348 s
    N=1000: 35.631503 J total, 35.6315 mJ/inference, 45.6709 W, 0.780180 s

Result:
- E1000 > E500 > E100: PASS
- E1000/E100 = 9.857 for a 10x workload increase
- relative spread of normalized energy: about 8.82 %
- exploratory population CV of normalized energy: about 3.87 %
- AC power and Windows power scheme remained unchanged within every run
- all three runs used the same hardware fingerprint

Phase 11 end-to-end plausibility is therefore accepted. The N=100 energy window
is only about 0.111 s and shows lower mean package power than the longer runs.
Phase 12 subsequently quantified this start-up/DVFS sensitivity using a fully
counterbalanced 18-run repeatability series.

4. Analyse the three result files
---------------------------------

PowerShell (single line):

    python -m bench.tools.energy_plausibility analyze <path-to-n100>\bench.json <path-to-n500>\bench.json <path-to-n1000>\bench.json --output phase11_energy_plausibility_report.json

The strict qualitative expectation is:

    E_1000 > E_500 > E_100

Energy per inference should be reasonably stable under comparable conditions. No
universal percentage tolerance is hard-coded. If a project-specific tolerance is
introduced later, its empirical/scientific justification must be documented.

5. Optional pytest gate for produced result files (PowerShell)
--------------------------------------------------------------

    $env:BENCH_ENERGY_PLAUSIBILITY_RESULTS = "C:\path\n100\bench.json;C:\path\n500\bench.json;C:\path\n1000\bench.json"
    python -m pytest bench/tests/integration/test_energy_plausibility_hardware.py -v

Optional project-specific threshold:

    $env:BENCH_ENERGY_PLAUSIBILITY_MAX_SPREAD_PCT = "<value>"

Remove the variables afterwards if desired:

    Remove-Item Env:BENCH_ENERGY_PLAUSIBILITY_RESULTS
    Remove-Item Env:BENCH_ENERGY_PLAUSIBILITY_MAX_SPREAD_PCT -ErrorAction SilentlyContinue

Scientific interpretation
-------------------------
A failed 100/500/1000 comparison is not automatically a software defect. Check:
- very short measurement window / sensor resolution,
- background processes,
- DVFS and frequency changes,
- thermal drift/throttling,
- different power/performance modes,
- cooling/temperature state,
- accidental model/input/batch/thread changes.

Do not add RAPL_Package0_PKG to PP0/PP1/DRAM. The subdomains are diagnostic and
can overlap with the package domain.

Phase 12 - Repeatability validation
==================================

Phase 11 status
---------------
Phase 11 is CLOSED on the Dell reference system. The optional pytest hardware
gate ``test_energy_plausibility_hardware.py`` is intentionally skipped during a
normal test run unless ``BENCH_ENERGY_PLAUSIBILITY_RESULTS`` is set. A repository
or CI runner cannot infer which external real-hardware ``bench.json`` files
belong to the validation series. The skip therefore means "no external hardware
artifacts were supplied to this optional gate", not "Phase 11 failed".

The gate can be executed explicitly on Windows, for example:

    $env:BENCH_ENERGY_PLAUSIBILITY_RESULTS = "C:\path\n100\bench.json;C:\path\n500\bench.json;C:\path\n1000\bench.json"
    python -m pytest bench/tests/integration/test_energy_plausibility_hardware.py -v
